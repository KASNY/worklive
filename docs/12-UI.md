# UI aplikacji

Interfejs WorkLive ma być spójny we wszystkich aplikacjach, czytelny w biurze, hali, magazynie i terenie oraz jednoznacznie pokazywać aktywny workspace.

## Źródło komponentów

Design system z `packages/ui` jest obowiązkowy dla każdej aplikacji WorkLive, która renderuje interfejs użytkownika. Dotyczy to strony marketingowej, panelu workspace, aplikacji mobilnej i desktopowej. API nie renderuje interfejsu.

Nie wolno tworzyć przypadkowych, lokalnych komponentów interfejsu poza `packages/ui`. Wyjątek jest dopuszczalny wyłącznie wtedy, gdy dokumentacja modułu uzasadnia komponent specyficzny dla aplikacji, określa jego właściciela i wyjaśnia, dlaczego nie jest elementem współdzielonego design systemu. Decyzja musi powstać przed implementacją.

## Kontrakt ekranu modułu

Każdy ekran musi zostać wymieniony w dokumentacji modułu przed implementacją. Opis obejmuje cel, odbiorców, dane, dostępne akcje, wymagane uprawnienia oraz zachowanie w stanach:

- ładowania;
- pustym;
- częściowych lub niedostępnych danych;
- błędu walidacji;
- błędu systemowego lub sieciowego;
- braku uprawnień;
- sukcesu.

Ekran lub akcja nieopisana w dokumentacji nie może zostać dodana „przy okazji”.

## Wspólne wzorce

- listy: udokumentowane wyszukiwanie, filtry, sortowanie i paginacja;
- szczegóły: status, kluczowe dane, relacje i dozwolone akcje;
- formularze: etykiety, pola wymagane, walidacja przy polu i podsumowanie błędów;
- destrukcyjne operacje: nazwanie skutku i świadome potwierdzenie;
- aktywny workspace: widoczny i niemożliwy do pomylenia z innym kontekstem;
- komunikaty: opisują problem oraz dostępny następny krok.

## Dostępność i urządzenia

Celem jest WCAG 2.2 AA: obsługa klawiaturą, widoczny fokus, semantyczne kontrolki, odpowiedni kontrast i cele dotykowe co najmniej 44 × 44 px. Web jest responsywny. Zakres poszczególnych aplikacji wynika z dokumentacji modułów, a nie z domysłów implementacyjnych.

Pierwszym językiem produktu jest polski. Kolejne języki wymagają decyzji w dokumentacji.
